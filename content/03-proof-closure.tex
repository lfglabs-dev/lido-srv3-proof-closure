\label{sec:proof-closure}

\noindent A local proof target is closed in this package when the executable
model check passes, the model and source anchors are listed, and the remaining
premises are named as assumptions. This section shows the fifteen accounting claims
in three forms: a system map, a plain-language story, and artifact rows for the
evidence package.

\subsection*{Modeled architecture}

\noindent The proof model follows the accounting path where PR \#1811 concentrates
fund-safety risk. In plain terms, the model follows ETH as it moves from the
Lido buffer, through the router, into staking-module deposits, and then into
later balance reports and reward calculations. Each proof asks whether that flow
preserves the accounting rule it is supposed to preserve. External contracts are
summarized only at the interfaces used by those transitions.

\subsection*{From intuition to target}

\noindent Read the fifteen properties as one accounting story. P1 protects ETH
reserved for withdrawals. P2 checks that initial deposits pull exactly the ETH
they should. P3 checks that the router's total balance equals the module balances
it accepted. P4 makes module fee weights depend on the accepted report, not an
old or partial one. P5 bounds reward and fee movement. P6 blocks non-active or
paused modules from deposit allocation and stopped modules from module-side
reward or fee allocation. P7 checks exited-count updates. P8 checks that top-up
allocation arrays are bounded and fully sunk. P9 checks SRv3's per-module
allocation-capacity rows before the external allocation strategy runs. P10 checks
the SRLib reward-minted reporting loop before module callbacks are attempted.
P11 checks the all-module fee-update arrays and module-config update loop.
P12 checks the single-module config-update guards that feed deposit allocation
and reward-fee configuration. P13 checks the governance-controlled module-status
update path that feeds the status-gating rules without changing validator-balance
accounting. P14 checks the module-creation path that extends the router module
array with a fresh, zero-accounting module. P15 checks the all-module
share-update loop that changes target-share and priority-exit thresholds without
changing module accounting balances.

\smallskip
\noindent Each invariant below has two layers. The first sentence says why the
property matters in ordinary accounting language. The formula then states the
same idea in a form that can be checked over all modeled inputs. You can read
the formulas like receipts: they name the money bucket before and after a move,
then check that the totals still match. The symbols below only stand for modules,
balances, reserves, and reports already described in the ledger story.

\smallskip
\noindent Let \(M\) be the finite set of staking modules in router order. For a
module \(m \in M\), let \(\bal_m\) be its accepted validator balance in gwei,
\(\modstatus_m\) its module status, and \(\mathsf{moduleRecipient}_m\) its module
reward recipient in the modeled reward step. Let \(B_R\) be the router validator balance, \(T\) the buffered ETH,
\(R_D\) the stored deposit reserve, and \(R_W\) the withdrawal-reserved buffer.
The checked theorems are in \path{LidoSRv3/Legacy/SpecProofs.lean}. Each accepted report must still cover the
current router module set in router order, with unique module IDs, matching array
lengths, and the freshness and range premises named in the target file.

\medskip
\noindent\textbf{P1: reserve separation.}
\[
  d = \min(T,R_D)
  \qquad
  w = \min(T-d,R_W)
  \qquad
  u = T-d-w
\]
\[
  \mathsf{depositable}(T) = d + u
\]
\[
  \mathsf{depositable}(T) + w = T
  \qquad
  \mathsf{depositable}(T) \leq T - w
\]
\[
  \forall a.\quad
  \mathsf{spendDeposit}(a) \Rightarrow
  a \leq \mathsf{depositable}(T)
\]

\noindent Plain reading: some ETH is saved for withdrawals, and deposits are not
allowed to spend that saved amount. The strengthened target proves the depositable
bucket and the effective withdrawal-reserved bucket \(w\) partition the buffer
exactly (\(\mathsf{depositable}(T) + w = T\)), so depositable ETH is bounded by
\(T - w\) and never includes withdrawal-reserved liquidity. This is derived from the
reserve definitions rather than assumed. The executable target deliberately avoids a
raw post-state equality for \(R_W\); any post-state reserve fact belongs to the
model's explicit reserve-recomputation rule.

\medskip
\noindent\textbf{P2: exact router pull.}
\[
  \mathsf{pulledWei}
    = 32\,\uniteth \cdot \mathsf{actualDeposits}
  \qquad
  \mathsf{routerEthAfter} = \mathsf{routerEthBefore}
\]
\[
  \mathsf{totalAllocatedDeposits}(\mathit{rows})
    = \sum_{(m,c) \in \mathit{rows}} c
  \quad \mbox{when only active modules carry a positive count}
\]
\[
  \mathsf{actualDeposits} > 0
  \Rightarrow
  \mathsf{pulledWei} \le \mathsf{depositableEtherBefore}
\]
\[
  \mathsf{actualDeposits} > 0
  \Rightarrow
  \mathsf{bufferedEtherAfter}
    = \mathsf{bufferedEtherBefore} - \mathsf{pulledWei}
\]
\[
  \mathsf{actualDeposits} = 0
  \Rightarrow
  \mathsf{bufferedEtherAfter} = \mathsf{bufferedEtherBefore}
  \quad\land\quad
  \mathsf{beaconSinkAfter} = \mathsf{beaconSinkBefore}
\]
\[
  \mathsf{withdrawalReserveAfter} = \mathsf{withdrawalReserveBefore}
  \qquad
  \mathsf{depositReserveAfter}
    = \mathsf{depositReserveBefore} - \mathsf{pulledWei}
\]
\[
  \mathsf{module.status} = \mathsf{active}
  \quad\land\quad
  \mathsf{maxDepositsCount} \ne 0
  \quad\land\quad
  \mathsf{actualDeposits} \le \mathsf{maxDepositsCount}
\]
\[
  M' =
    \mathsf{recordModuleLastDeposit}(
      \mathsf{stakingModuleId},\mathsf{pulledWei},M)
\]
\[
  \mathsf{selectedModule.lastDepositWeiAfter}
    = \mathsf{depositPullWei}(\mathsf{actualDeposits})
\]
\[
  |M'| = |M|
\]
\[
  \sum_{m\in M'} \bal_m = \sum_{m\in M} \bal_m
\]
\[
  \mathsf{routerBalanceGweiAfter} = \mathsf{routerBalanceGweiBefore}
  \quad\land\quad
  \mathsf{lastAcceptedReportAfter} = \mathsf{lastAcceptedReportBefore}
\]

\noindent Plain reading: across the modeled atomic initial-deposit transition,
the router pulls exactly one 32 ETH unit per validator only when that value is
available as depositable ETH, subtracts exactly that amount from modeled
buffered ETH, and immediately forwards it to the beacon deposit sink without
consuming the withdrawal-reserved bucket. The stored deposit-reserve bucket is
reduced by the same spend amount, saturating at zero, matching the Lido buffer
spend rule.
The zero-key return path records the selected module's last-deposit field but
does not move modeled value out of the buffer or into the beacon sink.
For both branches, the whole module array is exactly the
\(\mathsf{recordModuleLastDeposit}\) transformation of the pre-state array.
The successful transition also exposes the Solidity guard facts: the selected
module exists, is active, has nonzero computed capacity, and the returned deposit
count is within that capacity. It also checks the side effect that Solidity
performs before the zero-key return: the selected module's last-deposit field
records the exact pulled value, including zero, while preserving module-array
length, the router module-balance sum, and the stored router report state.
Top-ups are a separate Gwei-aligned allocation target covered by P8, not
instances of this 32 ETH exact-pull statement.

\medskip
\noindent\textbf{P3: module-balance conservation.}
\[
  \mathsf{acceptedReport}(M,\vec{b})
  \Rightarrow
  B_R' = \sum_{m \in M} \bal_m'
  = \sum_{i=0}^{|M|-1} \vec{b}_i
\]
\[
  \mathsf{successfulReportTransition}(r)
  \Rightarrow
  \mathsf{moduleBalances}' = \mathsf{reportBalances}(r)
\]
\[
  \mathsf{successfulReportTransition}(r)
  \Rightarrow
  M' = \mathsf{applyReportToModules}(M,r)
\]
\[
  \mathsf{successfulReportTransition}(r)
  \Rightarrow
  \mathsf{lastAcceptedReport}' = r
\]
\[
  \mathsf{successfulReportTransition}(r)
  \Rightarrow
  |M'| = |M|
\]
\[
  \mathsf{successfulReportTransition}(r)
  \Rightarrow
  \mathsf{ETHState}' = \mathsf{ETHState}
\]

\noindent Plain reading: the router total must equal the sum of the module rows
after a successful module-balance report transition. The modeled transition
preserves the Solidity length, router-order module-ID, and Gwei range checks
before applying the update loop, writes the submitted balance list into the
module balance fields exactly, proves the whole post-state module array is the
accepted report update-loop result, preserves the module-array length and
ETH-side state after that loop, then records the exact accepted report for the
reward-distribution read path.
The proof is over arbitrary finite module arrays; unique module IDs remain a
named well-formedness assumption rather than a hidden bound on module count.

\medskip
\noindent\textbf{P4: report-before-reward consistency.}
\[
  \mathsf{rewardStep}(s,s')
  \Rightarrow
  \exists r.\,
  \mathsf{acceptedAt}(r,s)
  \land
  \mathsf{rewardBase}(s)=\mathsf{balances}(r)
\]

\noindent Plain reading: accepted module balances determine the module
fee-distribution weights used by the modeled reward step. Total reward magnitude
and protocol fee inputs are treated as accepted report or vault-context inputs
subject to the listed range and freshness assumptions. In simpler terms, rewards
should be split using the report the system just accepted, not a previous
snapshot and not a half-updated table.

\medskip
\noindent\textbf{P5: reward-distribution loop and fee alignment.}
\[
  \mathsf{share}_m =
    \lfloor \bal_m \cdot \mathsf{precision} / \mathsf{totalBalance} \rfloor
\]
\[
  \mathsf{moduleFee}_m =
    \lfloor \mathsf{share}_m \cdot \mathsf{moduleFeeBps}_m / 10{,}000 \rfloor
\]
\[
  \mathsf{treasuryFee}_m =
    \lfloor \mathsf{share}_m \cdot \mathsf{treasuryFeeBps}_m / 10{,}000 \rfloor
\]
\[
  \bal_m = 0 \Rightarrow m \notin \mathsf{rewardDistributionRows}
  \qquad
  \mathsf{row}\in\mathsf{rewardDistributionRows}\Rightarrow \mathsf{row.balance}\ne0
\]
\[
  \mathsf{paidModuleFee}_m \leq \mathsf{moduleFee}_m
\]
\[
  \mathsf{totalBalance}=0
  \Rightarrow
  \mathsf{rewardDistributionRows}=[]
  \land
  \mathsf{map}(\mathsf{row.moduleId},\mathsf{rewardDistributionRows})=[]
\]
\[
  \modstatus_m = \stStopped
  \Rightarrow
  \mathsf{paidModuleFee}_m = 0
\]
\[
  \mathsf{totalFee} =
    \sum_{\mathsf{row}\in\mathsf{rewardDistributionRows}}
      (\mathsf{row.moduleFee}+\mathsf{row.treasuryFee})
\]

\noindent Plain reading: the modeled
\texttt{getStakingRewardsDistribution} loop returns no rows when the router
total validator balance is zero, and the returned module-id projection is empty
in that branch. Otherwise it emits rows only for modules with nonzero accepted
validator balance, keeps each row paired with the module's recipient, bounds
paid module-side fees by the computed module fee, and pays stopped modules zero
module-side fee. The total fee modeled for the final assertion is the sum of
every emitted row's module and treasury fee components.

\medskip
\noindent\textbf{P6: status gating.}
\[
  \modstatus_m \neq \stActive \lor \mathsf{depositsPaused}_m
  \Rightarrow
  \mathsf{allocatedDeposits}_m = 0
\]
\[
  \modstatus_m = \stStopped
  \Rightarrow
  \mathsf{paidModuleFee}_m = 0
\]

\noindent Plain reading: a stopped or paused module is not just marked differently
in storage; that status changes the allowed flow. Deposit-paused or non-active
modules receive zero modeled deposit allocation. Stopped modules receive zero
module-side fee or reward allocation. Any residual protocol-fee treatment is
stated separately from module recipient payment.

\medskip
\noindent\textbf{P7: exited-count update correctness.}
\[
  \mathsf{successfulExitedUpdate}(m,e')
  \Rightarrow
  \mathsf{existsModule}(m)
  \land e_m \leq e'
  \land e' \leq \mathsf{depositedValidators}_m
\]
\[
  \mathsf{successfulExitedUpdate}(\mathsf{rows})
  \Rightarrow
  |M'| = |M|
\]
\[
  \mathsf{successfulExitedUpdate}(\mathsf{rows})
  \Rightarrow
  (M',\mathsf{newlyExited})=\mathsf{sequentialExitedLoop}(M,\mathsf{rows})
\]
\[
  \begin{array}{l}
  \mathsf{successfulExitedUpdate}(\mathsf{rows},S,S')
  \Rightarrow \\
  \qquad
  \mathsf{nonModuleRouterState}' = \mathsf{nonModuleRouterState}
  \end{array}
\]

\noindent Plain reading: an accepted exited-count row cannot invent a module,
cannot move the router-stored exited count backward, and cannot report more
exited validators than the staking module summary says were deposited. The model
preserves Solidity's sequential loop behavior over arbitrary finite row arrays,
including duplicate module IDs, keeps the module array length unchanged, and
preserves the router module-balance sum and non-module router state. It also
proves that successful transitions return exactly the sequential loop result and
that the empty-row path returns the unchanged state with zero newly exited
validators.

\medskip
\noindent\textbf{P8: top-up allocation conservation.}
\[
  \mathsf{successfulTopUp}(m,\vec{a},\vec{\ell})
  \Rightarrow
  \mathsf{active}(m)
  \land \mathsf{supportsTopUp}(m)
\]
\[
  \mathsf{keyCount}>0
  \land
  |\vec{operatorIds}|=|\vec{\ell}|=|\vec{pubkeys}|=\mathsf{keyCount}
\]
\[
  |\vec{a}| = |\vec{\ell}|
  \land
  \forall i.\ \vec{a}_i \equiv 0 \pmod{1\,\mathsf{gwei}}
  \land
  \forall i.\ \vec{a}_i \leq \vec{\ell}_i
\]
\[
  \mathsf{topUpTarget}
  =
  \mathsf{roundDownToGwei}\bigl(
    \min(\mathsf{moduleAllocationWei},\,
         \mathsf{maxTopUpPerBlockGwei}\cdot 1\,\mathsf{gwei})\bigr)
\]
\[
  \sum_i \vec{a}_i
  \leq
  \mathsf{topUpTarget}
  \leq
  \mathsf{moduleAllocationWei}
  \qquad
  \sum_i \vec{a}_i
  \leq
  \mathsf{maxTopUpPerBlockGwei}\cdot 1\,\mathsf{gwei}
\]
\[
  \mathsf{topUpTarget} = 0
  \Rightarrow
  \mathsf{lidoCanDeposit} = \mathsf{true}
\]
\[
  \sum_i \vec{a}_i > 0
  \Rightarrow
  \sum_i \vec{a}_i \leq \mathsf{depositableEtherBefore}
\]
\[
  \sum_i \vec{a}_i > 0
  \Rightarrow
  \mathsf{bufferedEtherAfter}
    = \mathsf{bufferedEtherBefore} - \sum_i \vec{a}_i
\]
\[
  \sum_i \vec{a}_i > 0
  \Rightarrow
  \mathsf{beaconTopUpSink}' =
    \mathsf{beaconTopUpSink} + \sum_i \vec{a}_i
\]
\[
  \sum_i \vec{a}_i = 0
  \Rightarrow
  S' = S
\]
\[
  \sum_i \vec{a}_i > 0
  \Rightarrow
  \mathsf{routerEthAfter} = \mathsf{routerEthBefore}
\]
\[
  M' = M
\]
\[
  \mathsf{routerBalanceGwei}' = \mathsf{routerBalanceGwei}
  \qquad
  \mathsf{lastAcceptedReport}' = \mathsf{lastAcceptedReport}
\]
\[
  \mathsf{withdrawalReserveAfter} = \mathsf{withdrawalReserveBefore}
  \qquad
  \mathsf{depositReserveAfter}
    = \mathsf{depositReserveBefore} - \sum_i \mathsf{allocation}_i
\]

\noindent Plain reading: successful modeled top-ups preserve the Solidity
array checks around \texttt{allocateDeposits}, including nonempty input shape,
same returned allocation length, Gwei alignment, per-key limits, and the
capped, rounded module target, which also proves the returned sum stays inside
both the module allocation budget and the router-global per-block top-up cap
(\texttt{maxTopUpPerBlockGwei}, introduced at the re-pinned commit by
PR~\#1820). When the capped, rounded target is zero, the queue-advancement
no-op additionally requires the Lido protocol deposit gate
\texttt{LIDO.canDeposit()} to be open, matching the \texttt{LidoDepositsPaused}
revert added at the re-pinned commit. If the allocation sum is positive, the
router pulls exactly that amount from Lido only when it is available as
depositable ETH, then forwards it to the top-up deposit sink after subtracting
the same amount from modeled buffered ETH and the stored deposit reserve,
leaving no modeled router ETH residual and no withdrawal-reserve consumption,
and without mutating router module or report accounting.
If the checked allocation sum is zero, the modeled transition returns the
unchanged state after validation.

\medskip
\noindent\textbf{P9: allocation-capacity rows.}
\[
  \mathsf{row} \in
  \mathsf{modulesAllocationAndCapacity}(M)
  \Rightarrow
  \exists m \in M.\ \mathsf{row} = \mathsf{capacityRow}(m)
\]
\[
  |\mathsf{modulesAllocationAndCapacity}(M)| = |M|
\]
\[
  |\mathsf{allocatedCapacityValues}(\mathsf{modulesAllocationAndCapacity}(M))|
  = |M|
\]
\[
  \mathsf{map}(\mathsf{row.moduleId},
    \mathsf{modulesAllocationAndCapacity}(M))
  =
  \mathsf{map}(\mathsf{module.id},M)
\]
\[
  \mathsf{active}(m)
  \Rightarrow
  \mathsf{capacity}_m \leq \mathsf{targetValidators}_m
  \land
  \mathsf{capacity}_m \leq \mathsf{availableCapacity}_m
\]
\[
  \neg\mathsf{active}(m)
  \Rightarrow
  \mathsf{capacity}_m = \mathsf{currentAllocation}_m
\]

\noindent Plain reading: the modeled SRv3 allocation-capacity loop emits one row
per router module, preserves the module-id order in those rows, and keeps the
capacity-value array length aligned with the module array. Active module
capacity is bounded by both the stake-share target and the available module
capacity computed for initial deposit or top-up mode. Inactive modules do not
gain capacity; their capacity stays equal to their current allocation. The
external MinFirst strategy that turns these arrays into final deltas remains a
named assumption.

\medskip
\noindent\textbf{P10: reward-minted reporting guards.}
\[
  \mathsf{successfulRewardMintedReport}(\vec{id},\vec{s},\vec{r})
  \Rightarrow
  |\vec{id}| = |\vec{s}|
\]
\[
  \mathsf{successfulRewardMintedReport}(\vec{id},\vec{s},\vec{r})
  \Rightarrow
  \vec{r} = \mathsf{zipRows}(\vec{id},\vec{s})
\]
\[
  \mathsf{successfulRewardMintedReport}(\vec{id},\vec{s},\vec{r})
  \Rightarrow
  |\vec{r}| = |\vec{id}|
\]
\[
  \begin{array}{l}
  \mathsf{successfulRewardMintedReport}(\vec{id},\vec{s},\vec{r})
  \Rightarrow \\
  \qquad
  \mathsf{mapModuleIds}(\vec{r}) = \vec{id}
  \land
  \mathsf{mapTotalShares}(\vec{r}) = \vec{s}
  \end{array}
\]
\[
  row \in \vec{r} \land row.\mathsf{totalShares} \neq 0
  \Rightarrow
  \mathsf{existsModule}(row.\mathsf{moduleId})
\]
\[
  row.\mathsf{totalShares} = 0
  \Rightarrow
  \mathsf{skipBeforeModuleCheck}(row)
\]

\noindent Plain reading: the modeled \texttt{\_reportRewardsMinted} loop first
checks equal calldata-array lengths, constructs exactly one report row per
zipped module-id/share pair, preserves the module-id and share arrays in the
returned row projections, skips zero-share rows, and requires an existing module
id before any nonzero-share callback can be attempted. Callback effects,
low-level revert bytes, and event behavior remain named assumptions.

\medskip
\noindent\textbf{P11: all-module fee-update consistency.}
\[
  \mathsf{successfulFeeUpdate}(\vec{f},\vec{t},M,M')
  \Rightarrow
  |\vec{f}| = |M| \land |\vec{t}| = |M|
\]
\[
  \mathsf{successfulFeeUpdate}(\vec{f},\vec{t},M,M')
  \Rightarrow
  \forall i.\ \vec{f}_i + \vec{t}_i \leq 10{,}000
\]
\[
  \mathsf{successfulFeeUpdate}(\vec{f},\vec{t},M,M')
  \Rightarrow
  |M'| = |M|
\]
\[
  \mathsf{map}(\mathsf{moduleFeeBps},M') = \vec{f}
  \qquad
  \mathsf{map}(\mathsf{treasuryFeeBps},M') = \vec{t}
\]
\[
  \mathsf{successfulFeeUpdate}(\vec{f},\vec{t},M,M')
  \Rightarrow
  \sum_{m\in M'}\mathsf{balance}_m = \sum_{m\in M}\mathsf{balance}_m
\]
\[
  \mathsf{successfulFeeUpdate}(\vec{f},\vec{t},S,S')
  \Rightarrow
  \mathsf{nonModuleRouterState}' = \mathsf{nonModuleRouterState}
\]

\noindent Plain reading: the modeled \texttt{\_updateAllModuleFees} loop checks
that both fee arrays match router module count, accepts the empty-module case,
requires every row's module-plus-treasury fee sum to fit within total basis
points, requires all row sums to match the first row's sum, and updates module
fee and treasury-fee projections exactly to the supplied arrays without
changing the module-list length or router-stored validator-balance sum. It also
preserves ETH accounting, router report balance, and the last accepted report.

  \mathsf{successfulModuleParamUpdate}(m,p,M,M')

  \begin{array}{l}

  \end{array}
\]
\[
  \mathsf{successfulModuleParamUpdate}(m,p,M,M')

  \sum_{m'\in M'}\mathsf{balance}_{m'} = \sum_{m'\in M}\mathsf{balance}_{m'}
\]

  \begin{array}{l}

\]

  \begin{array}{l}

\]

\noindent Plain reading: the modeled \texttt{\_updateModuleParams} path checks
module existence, stake-share and priority-exit threshold ordering, bounded
module-plus-treasury fees, fee-sum consistency against every other module,
nonzero minimum deposit block distance, nonzero maximum deposits per block
(a precondition added at the re-pinned commit; checked by
\texttt{P12\_update\_module\_params\_requires\_positive\_max\_deposits}), and
uint64 bounds for deposit parameters
before updating the selected module without changing module-list length or
router-stored validator-balance sums. The post-state lookup for the selected
module records exactly the requested share, fee, max-deposit, and min-distance
fields. It also preserves ETH accounting, router report balance, and the last
accepted report.

\medskip
\noindent\textbf{P13: module-status update consistency.}
\[
  \mathsf{successfulStatusUpdate}(m,\sigma,M,M')
  \Rightarrow
  \mathsf{existsModule}(m)
  \land
  \mathsf{oldStatus}_m \neq \sigma
\]
\[
  \mathsf{successfulStatusUpdate}(m,\sigma,M,M')
  \Rightarrow
  |M'|=|M|
\]
\[
  \mathsf{successfulStatusUpdate}(m,\sigma,M,M')
  \Rightarrow
  \mathsf{statusOf}(m,M')=\sigma
\]
\[
  \begin{array}{l}
  \mathsf{successfulStatusUpdate}(m,\sigma,M,M')
  \Rightarrow \\
  \qquad
  \sum_{m'\in M'} \mathsf{validatorsBalanceGwei}_{m'}
  =
  \sum_{m\in M} \mathsf{validatorsBalanceGwei}_m
  \end{array}
\]
\[
  \begin{array}{l}
  \mathsf{successfulStatusUpdate}(m,\sigma,S,S')
  \Rightarrow \\
  \qquad
  \mathsf{nonModuleRouterState}' = \mathsf{nonModuleRouterState}
  \end{array}
\]

\noindent Plain reading: the modeled \texttt{\_setModuleStatus} path checks
