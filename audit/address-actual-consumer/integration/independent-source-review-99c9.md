Request owner occupies low160 bits, claimed is byte200–207; cumulative amounts are uint128 halves. Because the actual claim guard admits only zero claimed byte, markClaimed's addition of2^200 sets the intended byte without carry into neighbors. No new injectivity or arbitrary slot-disjointness premise is needed by the public consumers.
2. **EnumerableSet order and aliases.** A missing index causes the caller's assert panic. Nonzero index and zero length distinguish checked arithmetic panic; out-of-range deletion index distinguishes indexing panic. The conditional swap reads the actual tail value, writes the deletion cell, updates the moved member index, then pop re-reads the actual post-swap length. Pop clears the actual last cell, writes the decremented length, and only then deletes the removed index. The implementation does not assume these slots cannot alias. I inspected the retained solc0.8.9 harness bytecode/source map for the OZ pop statement: its cell-clear SSTORE at PC6163 precedes the length SSTORE at PC6165, matching this order. This is scoped compiler-artifact inspection, not full opcode-equivalence proof.
3. **Claim validation/calculation order.** Zero ID, finalization, claimed and owner checks precede marking and set removal. Hint/checkpoint/cumulative reads are taken after removal, so possible effects of physical-slot aliases are not discarded. Hint0, last checkpoint, current/next checkpoint interval, cumulative subtraction, zero shares and conditional discount multiplication follow the source order. Successful finalized/hint comparisons bound those Nat arguments by actual word reads. Each cumulative difference is bounded by uint128 storage, so multiplication by1e27 fits uint256; the variable shares×maxShareRate product is checked explicitly on the discount path. Locked ETH is freshly read after calculation/removal; successful subtraction derives payout≤locked<2^256, preventing hidden value truncation at the CALL.

Funding is checked against the actual Live balance; ordinary code-less recipients accept the transfer, while code-bearing recipient execution returns success/rejection and optional nested attempts. Successful callbacks supply the World actually used by subsequent operations. No callee balance/log preservation frame is assumed.
5. **Events, sequence and rollback.** WithdrawalClaimed and ERC721 Transfer are appended after the callback on its returned World, using fixed execution-context sender/recipient/requestId/payout rather than re-reading callback-mutated metadata. Batch recursion consumes that entire resulting World.
