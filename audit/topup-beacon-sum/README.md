The new result consumes successful `TopupModuleCall.execute`, retaining the actual module CALL, raw reply, decoded allocations, module-returned World, withdrawal/helper transitions, final World and chronological attempts from PR287. The existing physical helper ledger and slot32 effects remain part of that same result. No amount-admission, funding, capacity, non-alias, key-width, helper-success or no-wrap premise is supplied by its caller.

`loop_success_amount_bounds` derives each amount's loose uint64-gwei ceiling from the actual executed beacon guards. `loop_success_nonzero_bound` consumes PR286's necessary physical slot32 growth/capacity theorem. Together they bound the sum by `(2^32-1)*(2^64*10^9-1)`, below uint256. Zeros do not consume capacity. `helper_success_sum_fits`, `helper_success_guard_exact` and `positive_effects_sum` carry this fact through the actual helper and positive suffix; `module_execute_success_sum` applies it to the existing module executor. This is a backward necessary-effects proof, not a replacement execution or an unused adapter.

The genuine empty-key helper return remains explicit and may ignore allocations with an overflowing mathematical sum. A zero router total does not execute the helper, so this increment does not prove that a wrapped zero cannot arise from a malicious module response. No assumption is introduced to remove these source paths.
