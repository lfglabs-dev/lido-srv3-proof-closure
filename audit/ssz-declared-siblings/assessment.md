## Concrete missing byte connection and feasible proof route

Define the declared indexed-word view independently of loop termination:

`declaredWords raw offset count = (List.range count).map (fun j => rawWord raw (offset + UInt256.ofNat (32*j)))`.

This uses the pinned engine's actual zero-padded load and modular uint256 pointer arithmetic. It must not silently become a canonical ABI serializer or assume positive/aligned/nonwrapping offsets. SszWitnessAbi.tail deliberately admits signed relative offsets and its existing public lemma derives only count <=2^64−1. Preserve those semantics.

The promising proof chain is:

1. Existing330 success supplies 2<=count<=2^64−1, actual sourceWrapper success and Branch over proofWords. SszWrapperIndex.wrapper_success identifies the produced index as `appendIndex 11 (...)`; therefore index>=11, log2(index)>=3. This holds for arbitrary existing Configuration, not only the pinned50-sibling instance.
2. Prove the cursor arithmetic dichotomy for count>=2 and 32*count<2^256 (the latter follows from the executed uint64 count guard). With a single fixed32-byte stride and endpoint `offset+32*count` modulo256, the do-while cursor either exits after its first word because endpoint wrapped ahead of it, or traverses all count indexed words. This is a modular-arithmetic lemma, not a calldata-size or nonwrapping premise. It needs careful formal checking, especially initial-wrap and end-equality cases.
3. Existing `SszProofFold.branch_depth` says consumed length=produced index.log2. Thus the one-word early-exit alternative cannot be a successful complete330 run. Conclude `proofWords ... = declaredWords ...`, not just equal lengths.
4. Transport the existing Branch/tree statement to that complete declared view. Its count is the actual GI depth, hence 3<=count<=247 from uint248 index. The existing slotSibling equality and indexed-word identity give `declaredWords[count−2] = pairDigest(chunk slot,chunk proposer)`. The slot check and final validator authentication now provably use the same complete decoded list.

Do not replace these steps with a new `offset+32*count fits`, count cap, canonical calldata, successful intermediate loop or frame assumption. Do not use the older `verify_success_iff` with its supplied layout/resource premises as if330 had already discharged them. The actual330 Branch/depth and executed count guard are sufficient inputs to pursue this route. If the cursor dichotomy reveals a counterexample, report it and revise the increment; do not restrict the public domain to hide it.

This does not yet prove the declared range is a contiguous in-bounds host ByteArray.extract interval: modular/padded loads remain explicit. In particular a negative/signed relative offset that wraps immediately may traverse a full modular list. The useful claim is **every ABI-declared indexed word is authenticated**, with the precise source access semantics, not canonical encoding or arbitrary host-memory safety.

Proposed additive public consumer, e.g. `PSsz1.actual_compiled_cl_entry_complete_declared_branch`, should retain the entire330 branch/root/request/field/environment consequence and add the full indexed-word equality, count/depth bounds, penultimate sibling identity and independent Branch/tree over that complete list. ## Why a direct TOPUP330 adapter is not the smallest safe increment

Actual TopUpGateway204–228 invokes internal `_verifyValidator` after pubkey/sort/activation checks, with the existing gateway frame, a validator witness slice inside the original batch calldata, its selected index and physically selected withdrawal credentials. It then uses the same witness for headroom and produces the arrays consumed by the real module continuation. The CL helper44–57 has no external entry dispatcher of its own.

330 instead requires selector0x2e77b4ba, fixed head words4/36/68/100/132/164, and resets a standalone frame/free pointer128 in its prologue. Encoding each typed TOPUP Row into fresh harness calldata and running330 once per row would create a new execution/frame not present in the gateway. Calling the old typed verifier as well to obtain old success would also duplicate root/SHA execution. Neither is a source-faithful composition.

A real later lot needs an in-place compiled CL helper parameterized by actual gateway calldata locations/stack credentials/index, with memory and free pointer carried across rows. The outer batch decoder must derive those operands from the actual bytes, in actual order (activation reads precede verifier, other lazy fields occur within/after it). The decoded fields and complete proof list then feed the same row headroom and actual output arrays. Derive equivalence/projection to the entire existing typed TOPUP consumer on success, including actual root attempts and original rollback, without an independently successful verifier or arbitrary frame premise. The two worlds also need their existing declared relationship respected:330's EVM.State carries engine SHA execution, while the typed loop uses Live.World and a supplied typed Precompile; no universal SHA/compiler/gas relation may be smuggled in to join them.

That is a substantial follow-on integration, likely more than one bounded lot. The complete-declared-proof theorem removes one concrete prerequisite first and touches neither account_locator's active router-admission paths nor shared TOPUP execution files.
