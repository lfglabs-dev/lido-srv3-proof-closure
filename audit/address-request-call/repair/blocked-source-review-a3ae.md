Pinned `WithdrawalQueueBase.sol` defines the corresponding string-derived constants, and the seven vendored core bodies are byte-identical to core17005714. Queue and requestsByOwner base literals were separately checked and agree.

The new `AddressRequestCalls` imports and actively consumes both wrong names: enqueue reads last at line 72; requestWrites writes last-ID at line 56 and reads report timestamp from that post-write state at line 57. EnqueueEffect also uses the wrong last-ID reader, so the theorem proves the same incorrect addressing rather than repairing it. For a state whose actual last-ID slot contains 7 and the wrongly addressed slot contains 0, the modeled next ID starts from 0 while Solidity starts from 7. Likewise the constructor reads the wrong report-time word. This is not an outer ABI, gas, alias or caller-context boundary: it directly contradicts the physical queue-state correspondence claimed for the new consumed slice.

The isolated kernel/native fixtures use the imported wrong constants for their model setup, while the real Solidity fixture uses the correct source constants. Their separate successes therefore do not bridge this discrepancy. Exact identity with inherited accepted source is preservation evidence, not validation of a literal's correctness. The new path needs correct consumed positions and regressions/identity checks comparing those actual Lean literals with pinned Keccak/legacy assembly. Preserving the old historical bridge is compatible with adding correctly named constants specifically to the new variant; this report does not authorize or perform a particular implementation change. Any successor must refresh source identities, artifacts, scoped queries and affected tests before independent review.
